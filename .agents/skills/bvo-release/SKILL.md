# Релиз BvO Another

Полный выпуск: собрать актуальные карты выбранных языков без читов через [bvo-build](../bvo-build/SKILL.md), точечно обновить существующие номер и дату релиза в каждой, заменить карты в `Map/ross`, обновить ченжлоги и README, закоммитить изменения, выполнить push и опубликовать GitHub Release с проверенными картами.

Применяй только в репозитории `rossoliny/bvo-another`. Создание или обсуждение этого скилла не запускает выпуск. Учитывай явно заданный пользователем режим: только подготовка, черновик или публикация. Для полного выпуска по умолчанию нужна публикация сразу; согласованный запрос на полный выпуск включает commit, push, тег и GitHub Release, без повторных подтверждений тех же действий. Соблюдай ограничения текущего запроса и AGENTS.md; посторонние правки не включай.

До чтения истории, описаний прежних выпусков и сбора изменений примени [bvo-changelog](../bvo-changelog/SKILL.md): сначала сообщи число коммитов и получи подтверждение сканирования.

## Исходные данные

1. Проверь точный корень, ветку, `origin`, staged/unstaged/untracked изменения. До любых записей сохрани список существующих изменений. Не сбрасывай, не прячь и не коммить чужую работу. Не выбирай ветку `master` по памяти: определи текущую и целевую ветку репозитория.
2. Получи метаданные **последнего опубликованного обычного релиза** через GitHub (`gh release view` или REST `GET /repos/rossoliny/bvo-another/releases/latest`), его тег и SHA. Описание изучай после подтверждения объёма сканирования по `bvo-changelog`. Локальные теги, самый свежий коммит и черновики не заменяют эту проверку. Для сравнения при необходимости получи тег через `git fetch origin tag <tag>` и разреши SHA, включая annotated tags.
3. Если версия не задана, продолжи текущий порядок тегов `#1.3`, `#1.4`, …, увеличивая номер обновления как целое число. Проверь существующие релизы **и теги**, чтобы не занять уже использованную версию. Сохрани тег, ISO-дату `YYYY-MM-DD` из клиентского времени и URL вида `https://github.com/rossoliny/bvo-another/releases/tag/%231.4`. Для этого репозитория `#` в URL кодируется как `%23`.
4. Определи языки: по умолчанию `en,ru`, либо только явно выбранные пользователем. Зафиксируй HEAD и хеши входных файлов `w3x-content/`, `w3x-content-ru/` для RU, билда, упаковщика и `toolkit/build-w3x/localize-map.lua`. Основной JASS — `w3x-content/scripts/war3map.j`. Учитывай переносы из прежних `Current Script/`, `SLKs/`, `Objects/`, `trig_str/`, `Effects/`, `Sounds/`, `ReplaceableTextures/`: перенос файла сам по себе не изменение игрового поведения.
5. Определи содержимое выпуска до сборки. Если актуальные исходники содержат несогласованные незакоммиченные изменения, разреши их включение до публикации: карта, ченжлог и коммит тега должны описывать одни исходники. Не выпускай сборку из одного состояния под тегом другого. Если входные файлы изменятся в процессе, останови публикацию и повтори затронутые проверки для актуального состояния.

## Карта

Перед сборкой примени [bvo-prep-release-info](../bvo-prep-release-info/SKILL.md): передай номер выбранного тега без `#` и согласованную дату в формате `DD.MM.YYYY`. Подготовка меняет только существующие значения версии и даты в четырёх исходных файлах. После неё заново зафиксируй хеши входных файлов для проверки сборки.

Прочитай и примени `bvo-build`. Выполни из корня:

```bash
bash toolkit/build-w3x/build-w3x.sh --release --lang en,ru
```

Вместо `en,ru` передавай выбранный список языков. Требуются успешный exit code и упаковка с 0 errors / 0 warnings для каждого языка. Запиши итог проверки JASS, сообщённый билдом, и число переведённых полей RU; итоговые скрипты после обновления версии и даты обязательно проверь ещё раз из файлов, как показано ниже. Используй только свежие `build/BvO_Another_release_en.w3x` и/или `build/BvO_Another_release_ru.w3x` из этого запуска. Не запускай dev-сборку и не используй старые файлы из `build/` как замену.

RU подставляет только готовые TXT-тексты из `w3x-content-ru/`, с исходными именами файлов внутри архива; недостающие переводы остаются исходными. Не выполняй новый перевод при выпуске без отдельного запроса. Отрази неполноту перевода в описании выпуска, если она есть. JASS, WTS и бинарные объекты пока общие, поэтому INFO → Latest Version и существующие метаданные остаются на английском в обеих версиях.

Встроенные читовые функции, глобальные переменные, обработчики чата, таймеры и хуки урона должны отсутствовать в упакованном JASS. Сам факт передачи `--release` этого не доказывает. Оригинальный JASS и ресурсы не изменяются.

Текущий билд не принимает метаданные релиза. Используй [scripts/prepare-map.py](scripts/prepare-map.py) для **отдельной копии готовой карты**. Это дополнение к `bvo-build`, а не новая реализация сборки. Оно проверяет отсутствие читового кода и заменяет только существующие значения версии после `Rossoliny ` / `Release: ` и даты после `Date: ` в имени карты, lobby `SetMapName`, описании карты и INFO → Latest Version. Полный текст INFO, строки `Changelog`, `All Releases`, `Report bugs`, все ссылки, цветовые коды, переносы и базовая версия `v1.1a` сохраняются. URL аргумента подтверждает выбранный тег; существующие ссылки карты он не переписывает. Не заменяй описание раздела шаблоном и не добавляй новые строки при обновлении метаданных. Если нужные версия или дата отсутствуют, обработчик останавливается до записи; добавление недостающих строк требует отдельного запроса. Общие строки режима игры и исходники сохраняются. Для нового формата W3I или изменившейся структуры INFO обработчик останавливается с ошибкой; не обходи эту проверку.

Создай отдельный каталог выпуска внутри `build/`. Запусти обработчик через Python; он разрешает пути, проверяет границу `build/` и вызывает внутренний [stamp-release.lua](scripts/stamp-release.lua) через имеющийся тулкит. Аргументы — корень, вход, новый выход, тег, ISO-дата и точный URL. Например, для выбранного #1.4:

```powershell
# Из корня репозитория; значения версии и даты определены перед сборкой.
$releaseRepository = (Get-Location).Path
$releaseTag = '#1.4'
$releaseDate = '2026-10-11'
$releaseUrl = 'https://github.com/rossoliny/bvo-another/releases/tag/%231.4'
$releaseDirectory = Join-Path $releaseRepository 'build/release-1.4'
New-Item -ItemType Directory -Path $releaseDirectory
$releaseLanguages = @('en', 'ru') # Только языки, выбранные перед сборкой.
foreach ($releaseLanguage in $releaseLanguages) {
    $releaseMap = Join-Path $releaseDirectory "BvO_Rossoliny1.1a_11.10.2026_$releaseLanguage.w3x"
    python -B "$releaseRepository/.agents/skills/bvo-release/scripts/prepare-map.py" `
        --repository $releaseRepository --input "$releaseRepository/build/BvO_Another_release_$releaseLanguage.w3x" `
        --output $releaseMap --tag $releaseTag --date $releaseDate --url $releaseUrl
    if ($LASTEXITCODE -ne 0) { throw "Release metadata preparation failed: $releaseLanguage" }
    & "$releaseRepository/toolkit/JASSCraft113/pjass.exe" `
        "$releaseRepository/toolkit/JASSCraft113/common.j" "$releaseRepository/toolkit/JASSCraft113/blizzard.j" "$releaseMap.j"
    if ($LASTEXITCODE -ne 0) { throw "Final release JASS failed verification: $releaseLanguage" }
}
```

Подставляй выбранные значения, не копируй дату и номер из примера. Имя каждого asset должно быть уникальным для выпуска. Для единственной карты по указанию пользователя используй её игровое название без цветовых кодов и лишних суффиксов; для нескольких языковых карт добавляй `_en.w3x` или `_ru.w3x`, чтобы их различать. Для каждого языка отдельно запускай обработчик и проверку JASS. Обработчик сохраняет распакованный итоговый JASS рядом с картой для проверки; не загружай эти sidecar-файлы в GitHub.

Обработчик сверяет все игровые файлы архива каждой уже локализованной карты: допустимы только точечные замены версии и даты в JASS с INFO/названием и `war3map.w3i`, плюс версии во внешнем заголовке карты. При одинаковых входных версии и дате содержимое игровых файлов должно остаться побайтно прежним. Он сохраняет RU-тексты из входной сборки; не расширяй разрешённые изменения обработчика ради локализации. После проверки финальных JASS сверь исходные хеши и выполни минимальные актуальные игровые проверки, затронутые изменениями с последнего релиза. Не утверждай, что карты проверены в Warcraft III, если был только автоматический контроль. Сохрани SHA-256 каждой конечной карты.

Только после проверки всех выбранных языков замени соответствующие карты в `Map/ross`. Найди текущие пути в репозитории; учитывай согласованное пользователем переименование по игровому названию. При выпуске одного языка не заменяй карту другого и не загружай её старую сборку в новый релиз; удаляй ненужный языковой файл только по прямому указанию пользователя. Для каждого языка карта в `Map/ross` и asset должны иметь одинаковый SHA-256.

## Ченжлог и README

- Прочитай и примени [bvo-changelog](../bvo-changelog/SKILL.md) **до изучения коммитов и сбора изменений**. Обязательно сообщи число коммитов после последнего опубликованного релиза, включая ноль, и получи подтверждение названного объёма сканирования; для всей истории отдельно сообщи её размер.
- Базу сравнения задаёт пользователь. Если нужна оригинальная Unryze 1.1a, проверяй итоговую карту против оригинала, а не промежуточных релизов Rossoliny. Публичные EN/RU-тексты содержат только важные игровые различия понятным игрокам WC3 языком.
- Техническую историю, промежуточные проблемы/исправления, доказательства и результаты проверки храни в `docs/releases/<version>.md`. При переписывании текущего релиза сначала перенеси туда прежние полные заметки. Подготовленное описание для отправки в GitHub можно держать в `build/`, но это не единственное хранилище важной информации.
- В описании GitHub Release метаданные размещай одной короткой строкой в конце: база, дата и ссылка на точный коммит. Разделы сборки/проверки/читов и историю разработки в публичный ченжлог не включай.
- Обнови только ссылку актуального выпуска в `readme.md` и `readme.RU.md` на выбранный тег, сохранив остальное содержимое. Все ссылки, имена assets, дата и версия должны совпадать с картами и GitHub Release.

## Commit, push, публикация

1. Проверь полный task-owned diff, отсутствие секретов и несогласованных изменений. Перед staging повторно сравни существовавшие пользовательские изменения. Staging — только явный список согласованных файлов; никогда `git add .`, `git add -A` или wildcard. Изменения игровых исходников включай только в согласованном объёме. Каталог `build/` не коммить.
2. Перед commit проверь полный staged список и diff, `git diff --cached --check` и SHA-256 staged карты. Создай нейтральный коммит выпуска без AI/co-author атрибуции. Если staged содержимое пересекается с чужой работой, сначала разреши конфликт объёма.
3. Выполни обычный push целевой ветки. Проверь, что её удалённый SHA равен коммиту выпуска. При non-fast-forward остановись и исследуй состояние; force push не использовать. Не публикуй тег до успешного push.
4. Создай GitHub Release с новым тегом **на SHA коммита выпуска**, подготовленным названием/описанием и ровно одним проверенным `.w3x` asset на каждый выбранный язык. Для последовательного REST-выпуска допустим технический черновик до загрузки/проверки всех assets, затем публикация с `make_latest=true`. Полный выпуск должен завершиться опубликованным релизом, если пользователь не выбрал черновик.
5. Используй `gh`, если он установлен и авторизован, либо GitHub REST API. В этом окружении доступен Git Credential Manager: получай credentials только в памяти процесса через `git credential fill`, с `GIT_TERMINAL_PROMPT=0` и `GCM_INTERACTIVE=never`; не печатай ответ, token, headers и не записывай их в файлы. URL API и загрузки должны принадлежать GitHub и этому репозиторию. Body передавай структурированно или через `--notes-file`; не собирай многострочный текст shell-интерполяцией.
6. При неизвестном результате удалённого вызова сначала прочитай существующий релиз/тег/assets. Не создавай дубликат, не удаляй и не переопределяй опубликованный тег или релиз при повторе. Заверши только недостающий согласованный шаг.

## Проверка публикации

Проверь публичный статус, номер и дату релиза, SHA тега и удалённой ветки, точные ссылки в обоих README, список assets по выбранным языкам и SHA-256 каждой **скачанной** карты. Она должна совпадать с соответствующим asset, файлом в `Map/ross` и проверенной сборкой. Для полного выпуска проверь, что GitHub latest указывает на этот релиз. Повторно проверь сохранность посторонней работы и состояние Git.

В финальном ответе дай ссылку на опубликованный релиз, SHA коммита и краткий результат проверки карты. Если выпуск не завершён, точно назови выполненный шаг и препятствие; не называй черновик опубликованным релизом.
