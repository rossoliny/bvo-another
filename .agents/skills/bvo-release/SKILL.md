# Релиз BvO Another

Полный выпуск: собрать актуальную карту без читов через [bvo-build](../bvo-build/SKILL.md), встроить номер, дату и ссылку релиза, заменить карту в `Map/ross`, обновить ченжлоги и README, закоммитить изменения, выполнить push и опубликовать GitHub Release с картой.

Применяй только в репозитории `rossoliny/bvo-another`. Создание или обсуждение этого скилла не запускает выпуск. Учитывай явно заданный пользователем режим: только подготовка, черновик или публикация. Для полного выпуска по умолчанию нужна публикация сразу; согласованный запрос на полный выпуск включает commit, push, тег и GitHub Release, без повторных подтверждений тех же действий. Соблюдай ограничения текущего запроса и AGENTS.md; посторонние правки не включай.

## Исходные данные

1. Проверь точный корень, ветку, `origin`, staged/unstaged/untracked изменения. До любых записей сохрани список существующих изменений. Не сбрасывай, не прячь и не коммить чужую работу. Не выбирай ветку `master` по памяти: определи текущую и целевую ветку репозитория.
2. Получи **последний опубликованный обычный релиз** через GitHub (`gh release view` или REST `GET /repos/rossoliny/bvo-another/releases/latest`), его тег, SHA и описание. Локальные теги, самый свежий коммит и черновики не заменяют эту проверку. Для сравнения при необходимости получи тег через `git fetch origin tag <tag>` и разреши SHA, включая annotated tags.
3. Если версия не задана, продолжи текущий порядок тегов `#1.3`, `#1.4`, …, увеличивая номер обновления как целое число. Проверь существующие релизы **и теги**, чтобы не занять уже использованную версию. Сохрани тег, ISO-дату `YYYY-MM-DD` из клиентского времени и URL вида `https://github.com/rossoliny/bvo-another/releases/tag/%231.4`. Для этого репозитория `#` в URL кодируется как `%23`.
4. Зафиксируй HEAD и хеши входных файлов `w3x-content/`, билда и упаковщика. Источник карты теперь `w3x-content/`, основной JASS — `w3x-content/scripts/war3map.j`. Учитывай переносы из прежних `Current Script/`, `SLKs/`, `Objects/`, `trig_str/`, `Effects/`, `Sounds/`, `ReplaceableTextures/`: перенос файла сам по себе не изменение игрового поведения.
5. Определи содержимое выпуска до сборки. Если актуальные исходники содержат несогласованные незакоммиченные изменения, разреши их включение до публикации: карта, ченжлог и коммит тега должны описывать одни исходники. Не выпускай сборку из одного состояния под тегом другого. Если входные файлы изменятся в процессе, останови публикацию и повтори затронутые проверки для актуального состояния.

## Карта

Прочитай и примени `bvo-build`. Выполни из корня:

```bash
bash build-w3x.sh --release
```

Требуются успешный exit code и упаковка с 0 errors / 0 warnings. Запиши итог проверки JASS, сообщённый билдом; итоговый скрипт после добавления метаданных обязательно проверь ещё раз из файла, как показано ниже. Используй только свежий `build/BvO_Another_release.w3x` из этого запуска. Не запускай dev-сборку и не используй старые файлы из `build/` как замену.

Встроенные читовые функции, глобальные переменные, обработчики чата, таймеры и хуки урона должны отсутствовать в упакованном JASS. Сам факт передачи `--release` этого не доказывает. Оригинальный JASS и ресурсы не изменяются.

Текущий билд не принимает метаданные релиза. Используй [scripts/prepare-map.py](scripts/prepare-map.py) для **отдельной копии готовой карты**. Это дополнение к `bvo-build`, а не новая реализация сборки. Оно проверяет отсутствие читового кода, встраивает версию в имя карты и lobby `SetMapName`, дату и URL в описание карты и INFO → Latest Version. Общие строки режима игры и исходники сохраняются. Для нового формата W3I или изменившейся структуры INFO обработчик останавливается с ошибкой; не обходи эту проверку.

Создай отдельный каталог выпуска внутри `build/`. Запусти обработчик через Python; он разрешает пути, проверяет границу `build/` и вызывает внутренний [stamp-release.lua](scripts/stamp-release.lua) через имеющийся тулкит. Аргументы — корень, вход, новый выход, тег, ISO-дата и точный URL. Например, для выбранного #1.4:

```powershell
# Из корня репозитория; значения версии и даты определены перед сборкой.
$releaseRepository = (Get-Location).Path
$releaseTag = '#1.4'
$releaseDate = '2026-10-11'
$releaseUrl = 'https://github.com/rossoliny/bvo-another/releases/tag/%231.4'
$releaseDirectory = Join-Path $releaseRepository 'build/release-1.4'
New-Item -ItemType Directory -Path $releaseDirectory
$releaseMap = Join-Path $releaseDirectory 'BvO_Rossoliny1.1a_11.10.2026.w3x'
python -B "$releaseRepository/.agents/skills/bvo-release/scripts/prepare-map.py" `
    --repository $releaseRepository --input "$releaseRepository/build/BvO_Another_release.w3x" `
    --output $releaseMap --tag $releaseTag --date $releaseDate --url $releaseUrl
if ($LASTEXITCODE -ne 0) { throw 'Release metadata preparation failed' }
& "$releaseRepository/toolkit/JASSCraft113/pjass.exe" `
    "$releaseRepository/toolkit/JASSCraft113/common.j" "$releaseRepository/toolkit/JASSCraft113/blizzard.j" "$releaseMap.j"
if ($LASTEXITCODE -ne 0) { throw 'Final release JASS failed verification' }
```

Подставляй выбранные значения, не копируй дату и номер из примера. Имя asset должно быть уникальным для выпуска; сохраняй существующую конвенцию именования, пока пользователь не изменил её. Обработчик сохраняет распакованный итоговый JASS рядом с картой для проверки; не загружай этот sidecar в GitHub.

Обработчик сверяет все игровые файлы архива: допустимы только изменения JASS с INFO/названием и `war3map.w3i`, плюс внешнего заголовка карты. После проверки финального JASS сверь исходные хеши и выполни минимальные актуальные игровые проверки, затронутые изменениями с последнего релиза. Не утверждай, что карта проверена в Warcraft III, если был только автоматический контроль. Сохрани SHA-256 конечной карты.

Только после проверок замени `Map/ross/BvO_Rossoliny_1.1a.w3x` этой картой. Если канонический путь изменился, найди текущий по репозиторию; не создавай второй «актуальный» файл. Карта в `Map/ross` и asset должны иметь одинаковый SHA-256.

## Ченжлог и README

- Сравни фактическое содержимое последнего опубликованного релиза с выбранными исходниками и итоговой картой. Сообщения коммитов — указатели для поиска, не доказательство изменений. Проверяй каждый заявленный before/after по данным или коду; учитывай отменённые и промежуточные изменения и исключённые из release читы.
- Обнови `changelog/changelog_ru.txt` и `changelog/changelog_en.txt`: новый раздел с номером, датой и базовым релизом; накопительный текст сохраняй. Подготовь отдельное описание GitHub Release в `build/` на языке, выбранном пользователем, по умолчанию русском.
- Не переноси исправления вспомогательных карт в ченжлог основного релиза без доказательства различия опубликованных карт. Например, восстановление ассортимента Medal Exchange в промежуточном файле не доказывает изменение магазина между релизами.
- Обнови только ссылку актуального выпуска в `readme.md` и `readme.RU.md` на выбранный тег, сохранив остальное содержимое. Все ссылки, имя asset, дата и версия должны совпадать с картой и GitHub Release.

## Commit, push, публикация

1. Проверь полный task-owned diff, отсутствие секретов и несогласованных изменений. Перед staging повторно сравни существовавшие пользовательские изменения. Staging — только явный список согласованных файлов; никогда `git add .`, `git add -A` или wildcard. Изменения игровых исходников включай только в согласованном объёме. Каталог `build/` не коммить.
2. Перед commit проверь полный staged список и diff, `git diff --cached --check` и SHA-256 staged карты. Создай нейтральный коммит выпуска без AI/co-author атрибуции. Если staged содержимое пересекается с чужой работой, сначала разреши конфликт объёма.
3. Выполни обычный push целевой ветки. Проверь, что её удалённый SHA равен коммиту выпуска. При non-fast-forward остановись и исследуй состояние; force push не использовать. Не публикуй тег до успешного push.
4. Создай GitHub Release с новым тегом **на SHA коммита выпуска**, подготовленным названием/описанием и единственным проверенным `.w3x` asset. Для последовательного REST-выпуска допустим технический черновик до загрузки/проверки asset, затем публикация с `make_latest=true`. Полный выпуск должен завершиться опубликованным релизом, если пользователь не выбрал черновик.
5. Используй `gh`, если он установлен и авторизован, либо GitHub REST API. В этом окружении доступен Git Credential Manager: получай credentials только в памяти процесса через `git credential fill`, с `GIT_TERMINAL_PROMPT=0` и `GCM_INTERACTIVE=never`; не печатай ответ, token, headers и не записывай их в файлы. URL API и загрузки должны принадлежать GitHub и этому репозиторию. Body передавай структурированно или через `--notes-file`; не собирай многострочный текст shell-интерполяцией.
6. При неизвестном результате удалённого вызова сначала прочитай существующий релиз/тег/assets. Не создавай дубликат, не удаляй и не переопределяй опубликованный тег или релиз при повторе. Заверши только недостающий согласованный шаг.

## Проверка публикации

Проверь публичный статус, номер и дату релиза, SHA тега и удалённой ветки, точные ссылки в обоих README, список assets и SHA-256 **скачанной** карты. Она должна совпадать с asset, `Map/ross` и проверенной сборкой. Для полного выпуска проверь, что GitHub latest указывает на этот релиз. Повторно проверь сохранность посторонней работы и состояние Git.

В финальном ответе дай ссылку на опубликованный релиз, SHA коммита и краткий результат проверки карты. Если выпуск не завершён, точно назови выполненный шаг и препятствие; не называй черновик опубликованным релизом.
