# Ченжлог BvO Another

Публичный ченжлог объясняет игроку итоговую разницу между выбранной базой и выпускаемой картой. Журнал разработки сохраняет историю того, как эта разница была получена. Применяй в BvO Another вместе с текущим запросом пользователя.

## До изучения истории

1. Проверь корень, HEAD и пользовательские изменения. Получи через GitHub последний опубликованный обычный релиз, разреши его тег до полного SHA. Локальный тег или HEAD не заменяет эту проверку.
2. Используя только метаданные и `git rev-list --count`, посчитай коммиты после этого SHA. Пока не читай сообщения, diff, старые ченжлоги, содержимое карт и заметки об изменениях.
3. Сообщи пользователю название последнего релиза и число новых коммитов, **включая ноль**, и спроси подтверждение сканирования. Если нужна вся история для сравнения с оригиналом, отдельно назови её диапазон и количество коммитов.
4. Дождись прямого подтверждения названного объёма. Общее «делай», данное до сообщения чисел, не заменяет этот обязательный вопрос. До ответа можно исследовать правила оформления и готовить скилл, но нельзя собирать изменения. При расширении диапазона снова сообщи объём и спроси.

## Доказательство изменений

- Базу задаёт пользователь. Для сравнения с **оригинальной Unryze 1.1a** используй `Map/unryze/BvO_Another_v1_1a.w3x`, а не промежуточную Rossoliny, предыдущий релиз или старый текст ченжлога. Зафиксируй хеш оригинала и SHA проверяемого состояния в техническом журнале.
- Изучи все коммиты подтверждённого диапазона. Заголовки коммитов и прежние ченжлоги — только указатели: проверяй каждый кандидат по diff, исходникам и фактическим данным оригинальной и итоговой карты.
- Сравнивай итоговое поведение и значения. Перестановка SLK-столбцов, формат чисел, переименование символов, переносы файлов и восстановление потерь при разработке не доказывают игрового изменения.
- Учитывай отмены и последующие переработки. Сведи цепочку коммитов к одному итоговому отличию; одинаковое состояние в базе и выпуске не создаёт пункт ченжлога.
- «Исправлено» допустимо только для ошибки, существовавшей в выбранной базе. Если предмет или механика новые, опиши их добавление и конечное действие. Исправления их промежуточных багов, рецептов, иконок и очистки относятся в журнал разработки.
- Для каждого публичного пункта запиши в журнале: поведение в базе, поведение в выпуске и подтверждающие файлы/коммиты. Недоказанный пункт не публикуй; обозначь неопределённость в журнале.

## Публичный текст для игроков WC3

Аудитория знает только выбранную базу карты и не знакома с процессом разработки. Для оригинальной 1.1a не предполагается знание версий Rossoliny или Unryze 1.1c.

- Начни сразу с игровых изменений. Группируй по героям, предметам и игровым системам. Один короткий пункт описывает одно важное отличие; связанные значения можно объединить.
- Пиши, что игрок теперь может сделать или что происходит в игре: урон, дальность, стоимость маны, перезарядка, оглушение, замедление, условия применения, взаимодействие с предметами, выбор героя, арены и полезная статистика.
- Давай важные числа «было → стало» и конечные характеристики новых возможностей. Используй знакомые названия способностей и Q/W/E/R/T. Таблицы подходят для бонусов нескольких уровней.
- Убирай параметры без изменений. Когда неизменённое значение действительно нужно для понимания изменённой способности, пиши «не изменено относительно [базы]» / “unchanged from [baseline]”. Не пиши «сохранено», «сохранены», “preserved” или “retained” о неизменённых параметрах.
- Описывай результат простыми игровыми словами. Вместо «урон через движок», «событие урона» и технического добивания — подтверждённое взаимодействие молнии со щитами, блоком и отражением. Не обещай взаимодействия без проверки.
- Таймеры, очистка, хуки, глобальные переменные, rawcode, JASS, SLK, упаковка, SHA-256, pjass, число файлов, внутренние пути и результаты проверок остаются в журнале.
- Не добавляй разделы «Карты и проверка», «Релизные карты», «Средства разработки», команды читов, рассказ об объединении прежних релизов и пояснения о проведённой работе.
- Не описывай как изменения восстановление INFO, потерянных ресурсов или определений, удаление добавленной при разработке диагностики и исправления собственных промежуточных регрессий. Игрок оригинала этого не видел.
- Обновляй `changelog/changelog_ru.txt` и `changelog/changelog_en.txt` согласованно: одни факты, числа и объём, естественный язык каждого текста. Языки ченжлога не означают наличие двух языковых карт.
- GitHub Release содержит тот же игровой текст. Убирай повторения, технические таблицы и лишнее введение. В самом конце — одна короткая строка: база сравнения, дата выпуска, короткая ссылка на точный коммит релиза. Не добавляй рассказ о теге, `Map/ross`, составе коммита или «последнем игровом изменении».
- Список скачиваемых карт соответствует выбранным пользователем языкам. Если выпускается одна карта, не упоминай отсутствующую RU-версию. Имя файла используй как в игре, без цветовых кодов и лишних суффиксов, если так поручил пользователь.

## Журнал разработки

Храни технические сведения в **`docs/releases/<version>.md`**, в Git вместе с проектом. Это отдельный документ для разработчиков; публичное описание релиза не должно превращаться в его копию. Файл в открытом репозитории доступен читателю исходников, поэтому не называй его приватным.

Сохраняй там полную важную информацию: промежуточные работы и отмены, появившиеся проблемы и их решения, технические изменения, коммиты, результаты проверок и ограничения, хеши карт, таблицу доказательств публичных пунктов. При переписывании опубликованных заметок сначала перенеси их прежний полный текст и технические подробности в журнал; пометь обнаруженные ошибки базы сравнения, чтобы архив не воспринимался как проверенный игровой ченжлог. Прежние EN/RU-тексты можно разместить в раскрывающихся блоках.

## Проверка перед завершением

| Проверка | Требуемый результат |
| --- | --- |
| База и факт | Каждый пункт подтверждает конечное отличие именно от выбранной базы. |
| Новые возможности | Добавления не сопровождаются исправлениями собственных промежуточных багов. |
| Язык | Игрок WC3 понимает изменение без знания кода и истории разработки. |
| RU/EN | Факты и числовые значения совпадают; повторов нет. |
| Публичное / техническое | Игровые изменения публичны; история, доказательства и проверки в `docs/releases/`. |
| Публикация | Дата, коммит, выбранные карты и их названия соответствуют реальному выпуску. |

Проверь весь task-owned diff и сохрани пользовательские правки. Создание ченжлога само по себе не разрешает сборку, commit, push, изменение опубликованного тега или GitHub Release; действуй только в явно согласованном объёме.
